## 2. 브랜치 전략 (Branching Strategy)

- **전략**: Trunk-based Development (TBD) 지향
- **명명**: `feature/`, `fix/`, `refactor/`, `chore/` 뒤에 설명 추가

### 2.1 세부 원칙

- **작은 단위의 브랜치:** 하나의 브랜치는 오직 하나의 티켓(기능/버그)만 해결합니다.
- **단기 생명주기:** 브랜치는 생성 후 최대 48시간 이내에 `main`으로 머지되는 것을 권장합니다.
- **피처 플래그 활용:** 완성되지 않은 기능이라도 배포가 필요하다면 피처 플래그를 사용하여 `main`에 먼저 통합합니다.

### 2.2 예외 없는 브랜치 분기

코드·문서·설정을 막론하고 모든 변경 작업은 시작 전에 `feature/`, `fix/`, `refactor/`, `chore/` 접두어 브랜치를 먼저 생성한 뒤 진행한다. **`main` 에 직접 커밋하지 않는다.**

아래는 흔히 "예외처럼 보이는 상황" 이지만 모두 예외가 아니다.

| 상황 | 올바른 처리 |
|------|-------------|
| 저장소에 커밋이 0개 | 베이스라인 커밋 1개만 `main` 에 올린 뒤, 나머지는 `chore/initial-*` 브랜치에서 |
| 1인 개발 | Self-Review 도 PR 절차의 일부. 브랜치 → 머지 흐름 유지 |
| 원격 저장소 미연결 | 로컬에서도 브랜치/머지 동일하게 적용 |
| 초기 스캐폴딩·설정 변경 | "변경 단위가 작다" 는 이유로 `main` 직접 커밋 금지 |
| 한 줄짜리 오타 수정 | `fix/` 브랜치로 분기 |

판단이 모호하면 `main` 에 직접 커밋하지 않는다. 협업자에게 확인 후 진행한다.

## 3. 커밋 메시지 컨벤션

### 3.1 구조

```
<type>(<scope>): <subject>

<body>

<footer>
```

### 3.2 주요 타입

| 타입 | 설명 |
|------|------|
| `feat` | 신규 기능 |
| `fix` | 버그 수정 |
| `refactor` | 리팩토링 |
| `style` | 포맷팅 |
| `docs` | 문서 |
| `test` | 테스트 |
| `chore` | 기타 설정 |

### 3.3 작성 원칙

본문(body)은 '왜(Why)'와 '어떻게(How)' 위주로 기술한다. '무엇(What)'은 diff에 이미 드러나므로 반복하지 않는다.

---

## 4. PR 및 코드 리뷰

- **Atomic PR**: 작은 단위의 변경으로 분리하여 제출
- **Context**: 왜 바꿨는지 배경 설명 필수
- **Self-Review**: 제출 전 본인 코드에 코멘트 작성

---

## 5. 체크리스트

PR 제출 전 다음을 확인한다.

- [ ] 최신 `main` 동기화 여부
- [ ] 커밋 규칙 준수 여부
- [ ] 리뷰 가능한 적정 분량 여부
- [ ] 테스트 완료 여부
