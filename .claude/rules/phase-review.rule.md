## 2. 개요

각 저장소의 개발계획서가 정의한 **스테이지(S0~S7)** 완료 시 수행하는 검토 절차·수용 기준·기록 방식을 정의한다. 집보다는 **모노레포가 아닌 4개 개별 저장소**(zipboda-web/app/api/admin)로 구성되며, 각 저장소는 독립적으로 검토하되 공유 계약(xlsx 3종, `@zipboda/shared`)에 영향을 주는 변경은 합동 검토한다.

### 적용 원칙
- **수직 슬라이스 검증**: 해당 스테이지 산출물만으로 동작하는 최소 시나리오가 통과해야 한다.
- **계약 우선**: API 계약(API 정의서) 확정 후 클라이언트 병렬 진행. 실연동 시 임시 목 전량 제거(절대규칙 A1).
- **자동화 우선**: 자동화 가능한 검증은 반드시 자동화(CI), 수동은 자동화 불가 항목에 한정.

---

## 3. 스테이지 완료 검토 절차 (5단계)

1. **자동화 테스트 실행** — 타입체크·린트·단위/통합·빌드(저장소별 CI).
2. **회귀 테스트 실행** — 이전 스테이지 테스트 포함 전체 실행.
3. **교차 검토** — 저장소 리드 + 공유 계약 영향 시 관련 저장소 리드 합동.
4. **수용 기준 대조** — 해당 저장소 개발계획서 §6 "수용 기준(수치)" 항목별 대조.
5. **결과 기록·인수인계** — `/docs/reviews/stage-{S}-review.md` 기록.

---

## 4. 저장소별 자동화 게이트 (CI 필수)

| 저장소 | 필수 자동화 |
|--------|-------------|
| web | typecheck, lint, 단위/컴포넌트 테스트, build, (S2+) Lighthouse 성능/접근성 |
| app | typecheck, lint, 단위 테스트, EAS 빌드 검증 |
| api | typecheck, lint, 단위/통합 테스트, 마이그레이션 검증, (S7) 부하 테스트 |
| admin | typecheck, lint, 단위/컴포넌트 테스트, build |

---

## 5. 공통 수용 기준 (수치)

| 항목 | 기준 |
|------|------|
| 단위/핵심 로직 커버리지 | ≥ 80% |
| 웹 성능(LCP) | ≤ 2.5s (SSR 대상 페이지) |
| 3D 뷰어 프레임 | ≥ 30fps, 미지원 시 2D 폴백 |
| API 목록 응답 | P95 ≤ 500ms |
| 접근성(web/admin Lighthouse) | ≥ 90 (출시 스테이지) |
| 권한 우회 | 0건(인가는 서버 강제) |
| 커머스 동시성(2차) | 초과판매·중복결제 0건 |

세부 기준은 각 저장소 개발계획서 §6을 우선한다.

---

## 6. 검토 결과 기록 형식

`/docs/reviews/stage-{S}-review.md` (document-template-rule 규격 준수: 문서정보 + 변경이력). 포함: ① 자동화 테스트 결과 ② 회귀 결과 ③ 교차 검토 결과 ④ 수용 기준 대조 ⑤ 미해결(심각도 HIGH/MEDIUM/LOW·오너·해결 예정 스테이지) ⑥ 인수인계.

### 심각도·완료 규칙
- 모든 필수 항목 PASS + HIGH 0건이어야 스테이지 완료.
- HIGH: 해당 스테이지 내 해결. MEDIUM: 다음 스테이지 착수 전 계획 수립. LOW: 인수인계 기록.

---

## 7. 회귀·인수인계

- **누적 회귀**: 스테이지 S 완료 시 S0~S 전체 자동화 테스트 실행, CI에서 PR 머지 전 통과 강제.
- **인수인계**: 공유 계약(API 정의서 변경분·`@zipboda/shared` export·디자인 토큰)과 미해결 항목을 다음 스테이지 담당에게 전달.
- **저장소 간 정합**: 요구사항ID ↔ 화면ID ↔ API ID 상호 참조 미존재 0건 유지(대표 xlsx 기준).
